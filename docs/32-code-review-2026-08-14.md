## 一、已确认改造项（按优先级）

### 1. 锁的 stale 偷锁可导致跨进程 lost update（json-store / shared-board / message-bus）`[待实施]` — 高优先级

**位置**：

- `src/core/json-store.ts:92-96`（`acquireStoreLock`：锁文件 mtime 超过 staleLockMs（默认 30s）即删除重取，持锁期间不刷新 mtime）
- `src/core/shared-board.ts:371-414`（`tryAcquireMutex`：TTL 30s，同样不续期）
- `src/core/message-bus.ts:416-453`（`withMutex`：stale 判断 mtime > 30s）

**问题**：三个互斥实现都基于"锁文件 mtime 过期即可偷锁"。若一次写操作（大 store JSON 序列化 + fsync + `.bak` 复制 + Windows 杀软扫描）持锁超过 30s，第二个进程会删除锁并进入临界区，两个写者基于同一旧快照读-改-写，后写者覆盖先写者——**静默丢数据（lost update）**。三套实现还各自维护一套 stale/释放逻辑。

**解决思路**：

1. 持锁期间周期性刷新锁文件 mtime（如每 5s 重写 owner 与时间戳），使"活跃写者"的锁永不过期。
2. 或写后校验：释放锁前重读 store，若 mtime/内容指纹与进入临界区时不同则视为竞争（乐观并发）。
3. 收敛三套实现为同一个互斥模块（json-store 已有锁，SharedBoard/MessageBus 改为复用），消除策略漂移。

**验证**：新增确定性测试——模拟"写者持锁超时"（注入慢写或直接伪造旧 mtime），断言第二个进程不会偷锁、两个写者都成功且不丢更新；并发 worker 压力测试扩展为"慢写者 + 快写者"组合。

### 2. reconcileStaleAgentRuns 不校验进程存活，可能误杀活进程（run-registry + agent-runner）`[待实施]` — 高优先级

**位置**：

- `src/core/run-registry.ts:155-179`（心跳超 30s 直接标 failed 并清 pid，不检查进程是否真死）
- `src/agents/agent-runner.ts:997-1004`（controlTimer 心跳失败 → `requestTermination(1)` 主动杀进程）

**问题**：活进程若因磁盘竞争、系统挂起等原因心跳延迟，会被 reconcile 标记为 failed；随后其心跳调用抛 "not active"，agent-runner 捕获后**主动终止仍在工作的进程**。放大路径：多进程同时执行 GC/reconcile 时更易触发。

**解决思路**：

1. reconcile 前按平台检查 pid 存活：Windows `tasklist /FI "PID eq <pid>"`、POSIX `process.kill(pid, 0)`；进程确实不存在才收敛为 failed。
2. 或对"心跳过期但 pid 存活"的运行先发 stop_requested（给进程优雅收敛机会），再次过期才 failed。
3. 心跳失败时 agent-runner 不要立即 `requestTermination(1)`，改为记录并继续观察（除非 registry 明确已终态）。

**验证**：确定性测试——注入"心跳过期但进程仍存活"场景（fake invocation 子进程保持运行），断言 reconcile 不标 failed、不杀进程；新增"活进程心跳延迟"回归。

### 3. RpcInboxPump：失败 turn 的消息会被后续成功 turn ACK `[待实施]` — 中优先级

**位置**：`src/extension/rpc-inbox-pump.ts:142-183`（`onAssistantMessageEnd`）

**问题**：followUp 模式下第一次 `message_end` 失败（success=false）仅清 `waitingForCurrentTurnEnd/waitingForAgentStart` 并保留 activeBatch；若随后出现第二次成功 `message_end`，会直接进入 ACK 分支，把**失败 turn 的消息 ACK 掉**，违反"失败保留 lease redelivery"的注释意图（L156-163 的保留逻辑实际不可达）。

**解决思路**：`onAssistantMessageEnd` 在 `!success` 时立即清空 activeBatch（或标记 batch 为失败态，后续 message_end 不再 ACK 它），消息保持 delivered 状态等待 lease 到期 redelivery。

**验证**：rpc-inbox-pump 单测新增"首个 assistant turn 失败、后续 turn 成功"场景，断言失败批的消息不被 ACK、仍为 delivered。

### 4. shared-board 遗留死代码层：ESM `require` 潜伏炸弹与未接线黑板任务队列 `[待实施]` — 中优先级

**位置**：

- `src/core/shared-board.ts:247, 277, 551`（`listTasks`/`listHandoffs`/`listDecisions` 内 `require("node:fs")`）
- 同文件 `createTask/claimNextTask/completeTask/failTask/scheduleTaskRetry/cancelTask`（黑板任务队列）、`writeHandoff/readHandoff`、`writeDecision/listDecisions`

**问题**：项目为 `"type": "module"` + esbuild `format: "esm"`。已核对 dist 产物：esbuild 将 `require` 转为 `__require` shim，Node ESM 下 `typeof require === "undefined"` 会走 `throw 'Dynamic require ... not supported'` 分支（pi 的 jiti 加载若提供 require 才侥幸可用）。这些函数在生产代码**无调用点**（任务队列/handoffs/decisions 属已弃 M1–M6 体系），一旦未来接线即崩溃。

**解决思路**：删除整层遗留代码（黑板任务队列、handoffs、decisions 及其格式化函数），与 AGENTS.md"不恢复旧 M1–M6"一致；保留 `listMessages`（GC 在用，且其 `readdirSync` 来自顶部 import，无 require 问题）。删除前先 grep 确认无引用（`claimNextTask` 等仅内部互相调用）。

**验证**：删除后 typecheck + 全量单测；grep 确认 `require(` 在 src 下清零。

### 5. Message V1 单文件损坏阻塞整个 GC `[待实施]` — 中优先级

**位置**：`src/core/lifecycle-gc.ts:323` → `src/core/shared-board.ts:331-338`（`listMessages` 对每个文件 `JSON.parse` 无 try/catch）

**问题**：一个损坏的 `shared/messages/*.json` 会让 `/flux gc`（含 dry-run）整体抛错无法执行；Message V2 路径已有 warnings 降级（lifecycle-gc.ts:64-71），Message V1 没有，行为不一致。

**解决思路**：`listMessages` 逐文件容错（对齐 `archiveReadDirectMessages` L355-356 的 try/catch 跳过），GC 将损坏文件计入 warnings。

**验证**：lifecycle-gc 单测新增"messages 目录含损坏 JSON"场景，断言 GC 正常完成且 warning 含该文件。

### 6. DAG checkpoint 读取无防御 `[待实施]` — 中优先级

**位置**：`src/workflows/dag-executor.ts:431-444`（resume 分支）

**问题**：`JSON.parse` 无 try/catch；`nodeIds` 用 `JSON.stringify` 做**顺序敏感**比较（旧版本或字段顺序变化即误判不匹配）；无 schema 校验。损坏 checkpoint 使 Workflow resume 直接抛错。

**解决思路**：

1. `JSON.parse` 包 try/catch，失败抛带路径的可读错误（或降级为"checkpoint unavailable"并允许 planner 重跑）。
2. nodeIds 比较改为顺序无关的集合比较。
3. 对 checkpoint 关键字段（completed/failed/taskResults/artifactPaths 形状）做最小 schema 校验。

**验证**：test-dag-contracts 新增：损坏 checkpoint 抛可读错误；nodeIds 乱序但同集合视为匹配；缺字段 checkpoint 拒绝恢复。

### 7. quality-gate 子进程无进程树管理、进程逻辑重复 `[待实施]` — 中优先级

**位置**：`src/workflows/quality-gate.ts:240-263`（spawn/kill/usage 解析为第二套简化实现）

**问题**：超时/abort 只 `proc.kill("SIGKILL")` 主进程，Windows 上 judge 内部派生进程可能残留；且与 agent-runner 的进程管理（taskkill /T、detached、缓冲截断）重复实现，易再引入 agent-runner 已修过的 bug（如缓冲无上限 L287-292 同样存在）。

**解决思路**：短期——补进程树 kill（复用 `terminateProcessTree` 思路）与缓冲上限；长期——将 judge 也走 `runAgent`（用最小 tools/thinking=off 配置），消除重复。

**验证**：test-dag-contracts 补 judge 超时后无残留进程断言（沿用 tests/helpers/hanging-process-tree.cjs 风格）。

### 8. 子进程 stdout/stderr 缓冲无上限 `[待实施]` — 低优先级

**位置**：`src/agents/agent-runner.ts:1047-1053`

**问题**：`buffer += data.toString()` 与 stderrBuf 无大小上限（output 只在 join 后截 50K），异常大的输出可耗尽内存。

**解决思路**：流式按行解析（现逻辑已是按行，但 buffer 本身需设上限，如 64MB 后丢弃并标记截断）；stderrBuf 参照 quality-gate L294 的 `.slice(-8000)` 做法。

**验证**：子进程安全生命周期测试新增"超大输出"场景（fake 子进程持续输出），断言进程正常结束、内存有界、结果被截断标记。

## 四、产品改进意见（评审结论，非功能承诺）

### 1. 数据生命周期治理（最高优先级）

Task/Execution/Run/Telemetry 全部无限增长且 GC 不清理 runs/tasks/events——长期使用必然性能劣化与磁盘膨胀。建议：GC 增加终态 runs/tasks 保留上限与 telemetry 轮转；TUI 提供历史归档/导出；文档明确各文件增长模型。

### 2. Main 会话成本与缓存可观测性

子 Agent 有完整 usage（checkpoint.json）、Persistent 有累计 callCount/cost，唯独 Main 每轮 input/output/cacheRead/cost 无记录（executions 成本恒 0，`/flux status` 中 Main 的 totalCostUsd 恒 0）。用户无法回答"这个项目到底花了多少钱、缓存命中多少"。按 .codex/CONTINUATION.md 第五阶段-5 既有方案实施：agent_settled/turn_end 时从 message_end 读取 usage 落盘。

### 3. Community 协作闭环

当前是"Main 主持的状态机"：无参与者主动认领/讨论循环、无预算/无进展/最大轮次停止条件、无 Proposal/Decision 实体。优先补"停止条件"（防止无人认领的 issue 永久挂起），再按阶段 3b 设计讨论推进。

### 4. Workflow 的 lockFiles 语义过强

planner 生成的 `node.files` 被直接用作运行时硬锁（`dag-executor.ts:738`）——模型生成的 files 不完整/不准确时实现者被锁死在错误的文件集上（docs/31 已有任务本体成功但被误判的先例）。建议：files 降级为"冲突检测提示 + 串行化依据"，实现者可通过消息或二次规划显式扩展；judge 仅截断 8000 字符输出，长产出易误判（`quality-gate.ts:184`）。

### 5. 错误可诊断性

失败只给 500 字符截断消息 + 无解释的 exit code（73/74/75/76/77）。建议：通知固定附详情路径（checkpoint/artifact）；帮助文档提供 exit code → 用户可读解释表；失败任务可一键查看完整 error。

### 6. TUI 三套入口并存

tools + `/flux` 命令族 + 分层菜单三套入口，`/flux work workflow <task>` 命令文本长且嵌套深。建议：菜单为默认入口，命令帮助按高频路径重排（work/agent/task/issue），菜单选项文案与命令帮助对齐。

### 7. 成本透明细节

未知模型成本显示 $0（UNKNOWN_PRICE）易误读为免费——建议统一显示"?"/"价格未知"；`loadPricing` 首启串行拉双源最坏阻塞 30s（`pricing.ts:349-366`），建议并行或缓存预热。

### 8. 发布与验证面

CI 增补 Windows runner（§二）；live 测试成本受控策略已很好，建议把"每轮真实链路冒烟"纳入发布 checklist。
